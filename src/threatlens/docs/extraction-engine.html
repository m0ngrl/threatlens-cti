Extraction Engine

The extraction engine turns a CTI report (PDF or plain text) into a typed set of candidate indicators of compromise, plus document metadata. It works in two stages that are kept strictly apart:

  • a candidate stage: deterministic regex rules decide where something worth looking at is in the text, and
  • a verification stage: a verifier reads each candidate's surrounding text and decides whether it is an IoC the report's authors are actually presenting.

Verification classifies; it never extracts. Every value in the output was found by the regex stage at a known offset, so a verifier cannot invent an indicator, and the start/end offsets can be trusted.

Two engines, one front end

There are two engines, chosen per run as llm (the default) or python. They are two modules, but not two separate extractors:

ioc_extract_llm_fs.py owns the shared front end: reading, metadata, candidate extraction, the domain model (Extraction, Verification, IoCExtractionResult, …). ioc_extract_python.py imports all of that and adds only its own verifier. The consequences:

  • For the same report, both engines produce the identical candidate set: same values, same offsets, same candidate ids (stable_id, a hash of category, type and normalised value). Only the verdicts differ.
  • Both return the same IoCExtractionResult object, so every caller handles either engine with the same code.
  • A change to reading or candidate extraction belongs in ioc_extract_llm_fs.py; the python engine picks it up automatically.

The engines are alternatives, not a pipeline: a single run uses exactly one of them. They meet in two places. If a report already in the database is ingested again with the other engine, its source is marked extraction_engine = 'llm+python' instead of being overwritten. And the quality checker can grade how far the two engines agree, but only when given both engines' JSON from its own command line (see Hand-off).

Steps 1–3: the shared front end

  • Reading. PDFs are read with PyMuPDF (page text joined in order). Text is normalised to repair artefacts that would break indicators: hyphenated tokens wrapped across lines, and Markdown escape backslashes that split defanged values such as example\[.\]com. The SHA-256 of the file bytes becomes the document's identity in the database.
  • Candidates. CTIExtractor runs the RULES table (34 typed regex rules: URLs, IPv4/IPv6, hashes, file names and paths, registry keys, e-mail, CVEs, crypto addresses, and more), then dedicated passes for domains, hostnames, scheme-less URLs, e-mail domains and intelligence entities (malware, threat actors, campaigns, tools). Defanged forms (hxxp, [.], [at]) are matched and refanged. Candidates nested inside a longer candidate are removed, and duplicates (same category, type and normalised value) are collapsed, keeping the one with the longest excerpt.
  • Deliberately over-inclusive. This stage is built for recall. It is meant to catch everything shaped like an indicator and leave the judgement to verification.

Steps 4–6: LLM verification

  • Profile once. DocumentProfiler sends the title, section headings and the first 2,000 characters (not the whole report). It gets back a short structure summary, such as "section 4 lists victim organisations, not attacker infrastructure", and a scope (tactical, operational or strategic) with a reason. A separate profiler model can be configured; by default it is the verifier model.
  • Verify in batches. LLMVerifier sends batch_size candidates per request (threatlens.conf [llm] batch_size; 5 by default, set by threatlens-calibrate). Each request carries the document metadata, the structure summary, and for each candidate its type, value, attributes and excerpt. The model never sees the whole document. It answers under a written rubric: citations, vendor pages and benign examples are rejected; malware names, actors, CVEs and ATT&CK techniques are context_entity; a value in the report's own IOC table is confirmed_ioc; and so on. Each decision comes with a confidence, a reason and an evidence quote.
  • Deterministic, structured output. Requests use Ollama's JSON-schema structured output at temperature 0 with thinking disabled, so the same model, settings and input give the same answer. The ex3 and ex4 runs produced identical results (see the deviation report).
  • Retries. A response is only checked structurally: valid JSON, and exactly one decision per candidate id. A failing batch is retried up to max_retries times; a truncated response grows num_predict and num_ctx before the retry. If a batch still fails, it is split in half and each half is retried on its own (recursively), since a failure that repeats at temperature 0 is deterministic and only a different request routes around it. Only a single candidate that still fails aborts the report.
  • Scope assessment. _assess_scope combines the profile's scope with flags taken from the accepted candidates: tactical content (network/host/e-mail observables), operational content (behaviour or TTPs) and strategic content (the profile itself).

Step 4 (python engine): heuristic verification

HeuristicVerifier checks rules in a fixed order and stops at the first that fires:

  1. intelligence entities → context_entity (or rejected in pure reference context);
  2. behaviour descriptions → context_entity;
  3. reference wording just before the value, or a match on the report's own source → rejected;
  4. per-type rules for e-mail addresses, hashes, host artefacts and network observables, using an IOC-section heading, malicious-context words (MALICIOUS_CONTEXT_RE), malicious actions (MALICIOUS_ACTION_RE), defanging and benign wording;
  5. otherwise uncertain.

Why regex alone isn't enough, and why the LLM is the default

Left unchecked, the candidate stage produces plenty of noise: a citation URL, a vendor's own domain, an ATT&CK name that looks like a cryptonym, a victim's domain in a targets table, a signed binary mentioned only because malware abused it. Whether such a value is an IoC depends on what the surrounding sentence, or the report's structure, says. Matching the string itself cannot settle it.

The python verifier narrows the gap with keyword rules one layer up, but with the same limits:

  • No semantic reasoning. "No record of malicious activity was found at example.com" contains the same trigger words as a real detection.
  • No document-level context. Without a profile it cannot tell a victims table from an infrastructure table, or a side-loaded signed binary from the payload dropped beside it.
  • No justification. A keyword hit produces a status directly, with no explanation in terms of the actual sentence.

The LLM reads the excerpt against a written rubric and the document profile, and explains each decision. That is why it is the default; the python engine is there for when no LLM is available.

The verdict is final within the engine

analyse_document() attaches each verifier decision to its candidate unchanged. Nothing in the extraction engine adjusts, blends or second-guesses a verdict. Downstream, the quality checker can still reject a candidate on structural or STIX grounds whatever the verdict, but it does not re-run verification.

Why there are two routes

  • The CLI is for looking, not storing. It runs only the extraction stage, so a change to the extractor, or the difference between the two engines, can be examined on one report without creating database rows. Its JSON output is a complete record of what the engine decided.
  • The web UI is for ingesting. Extraction is only the first of four steps, and the Ingest page needs the other three. There is one implementation of that pipeline, ingest_worker.py. The Ingest page, threatlens-ingest and the batch runner all use it, so a database built from the terminal matches one built from the browser.
  • The dashboard runs the engine in a separate process. An LLM run takes minutes. In a worker process it can be cancelled by killing the process, a crash in the extractor cannot take the dashboard down, and the worker's verbose log can be streamed to the page live. Jobs run one at a time because every job writes the same SQLite file and one LLM job already keeps Ollama busy.
  • The engine has no command-line or web code of its own in either route. Both callers pass in already-resolved settings and get back a Python object, so the engine stays testable on its own.

Settings

The python engine reads no settings. For the llm engine, both cli.py and ingest_worker.py take every setting from threatlens.conf, with built-in defaults for anything it leaves out: the Ollama URL ([ollama]), the verifier and profiler models ([models]) and the performance tuning ([llm]: batch size, timeouts, context sizes, retries). extractors/calibration.py (threatlens-calibrate) benchmarks the server and writes [ollama], the verifier model and [llm]; the dashboard's Configuration page edits the URL and models and keeps [llm]. (These used to be split with a separate llm_calibration.conf, looked up in the current directory by the CLI but in the repo root by the worker; there is now one file and one lookup.) Before an llm run, both callers print a warning for each setup step not yet done. See CLI for the full table and calibration.

Hand-off

The engine's output is always an IoCExtractionResult. How it leaves the engine depends on the caller.

From the CLI: JSON, on request

IoCExtractionResult ──to_dict()──▶ JSON file (-o)
                                     │  optional, by hand:
                                     ▼
                     python -m threatlens.quality.quality_checker out.json [--compare other.json]
                                     │  load_run() → check_report()
                                     ▼
                              printed quality report (no database)

The JSON contains metadata, verification_model, scope, summary, every candidate in indicators (with its verification), and accepted_by_category. The quality checker reads this format directly. Giving it both engines' JSON for the same report (--compare) is the only place the two verdicts are graded against each other. See CLI.

From the web UI and threatlens-ingest: in memory

IoCExtractionResult
      │  quality_checker.run_from_payload(result)   (calls result.to_dict(); no file)
      ▼
ExtractionRun ──▶ check_report([run], policy from the database's scoring_config)
      │
      ▼
QualityReport ──▶ persist_report() ──▶ sources, raw_documents, indicators,
      │                                 sightings, quality_flags   (commit)
      ▼
rescore_from_db() ──▶ timeliness / accuracy refreshed for stored indicators (commit)

The worker never writes the result to disk. It runs one engine, so check_report gets a single run and every candidate's agreement grade is single_verifier. What travels where:
